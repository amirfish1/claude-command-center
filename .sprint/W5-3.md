# Lane W5-3 — Restart API doesn't actually reload code

Updated: 2026-09-03 20:55
Status: DONE — fixed, tested, verified live on :8099, committed
Owner: CCC lane W5-3 (dispatched by 25c52af6-c616-46a2-b47d-0f8a9e016055)

## Root cause
`_schedule_restart()` (dashboard) and `_restart_worker_process()` (worker)
both decided "safe to trust `launchctl kickstart -k <label>`" purely from
`plist_path.is_file()` — i.e. "is the LaunchAgent plist installed on disk
anywhere", not "does launchd actually supervise the process that received
this request". A plist existing is true for the real dashboard on :8090
*and* for any manually started dev/duplicate instance
(`CCC_ALLOW_DUPLICATE_REPO=1 PORT=8099`) or stray leftover process, since
they all share the same on-disk plist file and launchd label.

So a restart POST to a non-launchd-owned instance kickstarted the *real*
launchd job (a different, unrelated process) — `returncode == 0`, reads as
success — while the actual live process that received the request (and
still holds the port) was never touched and kept serving old code. Matches
the exact symptom: `{"ok": true, "restart": true}` but `/api/version`
uptime keeps counting.

## Fix (server.py)
- `_launchd_job_pid(label)`: parses `launchctl list <label>`'s `"PID" = N;`
  line, or None if the job isn't currently running under that label.
- `_launchd_restart_targets_pid(label, expected_pid)`: the decision —
  safe when nothing is running under the label yet (kickstart starts it
  fresh, nothing to conflict with) or the tracked PID matches; unsafe when
  a *different* PID owns the label (kickstart would hit the wrong process).
- `_schedule_restart()` now calls this with `os.getpid()` before trusting
  kickstart; falls to `os.execvp` self-restart otherwise (always correct —
  it restarts whoever is actually running this code, launchd or not).
- `_restart_worker_process()` same guard with the worker's known pid
  (`worker.get("pid")`) before trusting kickstart; falls to kill+respawn
  otherwise (existing fallback, now reached correctly instead of a false
  "launchd" success).
- Added a build stamp: `_SERVER_CODE_REV` = `git rev-parse HEAD` computed
  once at import time (frozen for the process's life, unlike the existing
  `_ccc_last_updated_iso()` which re-forks git per `/api/version` call).
  Exposed as `code_rev` on `GET /api/version`, and as a `"before"` snapshot
  `{code_rev, started_at, pid}` on `POST /api/restart`(`/all`) — there's no
  synchronous "after" (the process gets replaced/handed to launchd before
  it could reply), so callers verify by polling `/api/version` until
  pid/started_at change and `code_rev` matches current `git rev-parse HEAD`.

## Fix (ccc CLI)
- `ccc doctor` now also fetches `/api/version`, compares its `code_rev`
  against local `git rev-parse HEAD` (`_local_head_rev`), and prints
  `server: code matches HEAD (...)` or `server: STALE CODE — ... restart
  needed`. Exit code is now 1 when stale, even without `--engine`.
  `--json` gets an additive `code_freshness: {status, running_rev,
  local_rev}` block.

## Live verification (isolated instance, never touched :8090)
`CCC_ALLOW_DUPLICATE_REPO=1 PORT=8099 python3 server.py` (pid 88964, no
launchd job of its own):
- `GET /api/version` → `code_rev` present, matches `git rev-parse HEAD`.
- `POST /api/restart` → `{"ok": true, "before": {...pid 88964...}}`;
  confirmed the *real* dashboard's launchd PID was untouched by this call
  (its PID change during the window was independent/pre-existing, checked
  by timestamp — ~8 min before this test, not caused by it); the dev
  instance's own `started_at` advanced in place (same pid 88964,
  `os.execvp` fired, not a launchd kickstart) — exactly the fix's intent.
- `ccc doctor` (via `CCC_SERVER=http://127.0.0.1:8099`) printed
  `server: code matches HEAD (...)`, `--json` carried `code_freshness`.
- Instance killed after verification.
